# Question Playbook

ヒアリング時に毎回全部聞くのではなく、曖昧さを減らすために必要な質問だけを選ぶための補助資料です。

## 1. Ambiguity Triage

### Low ambiguity

特徴:

- 目的は分かる
- 何を作るかもおおむね分かる
- ただし入力、出力、制約、例外が足りない

聞くべきこと:

- 完了条件
- 対象データや対象範囲
- 既存との互換性
- 例外ケース

### Medium ambiguity

特徴:

- 作りたいものはあるが、誰のためか、何を優先するかが曖昧
- 成功の定義が曖昧

聞くべきこと:

- 誰が困っているか
- 何がどう変われば成功か
- いちばん困る失敗は何か
- 制約と優先順位

### High ambiguity

特徴:

- 解決策しか出ていない
- 目的、背景、利用場面がほとんど見えない
- 抽象語が多い

進め方:

- 最初にヒアリングを行う
- 問題、期待成果、対象ユーザーが見えるまで仕様化を急がない

聞くべきこと:

- その依頼で最終的に何を変えたいか
- 今どんな問題が起きているか
- なぜ今それが必要か
- 実装以外の代替策でもよいか

## 2. Deliverable Mode Selection

質問と最終成果物の重心は、次の3モードから選ぶ。

### Implementation

向いている依頼:

- API や UI の仕様を詰めたい
- 実装前提の要件整理をしたい
- バグ修正や機能追加の受け入れ条件を明確にしたい
- データ、状態、外部連携、例外処理を定義したい

重くする論点:

- 入出力
- 挙動
- データと状態
- 例外ケース
- 受け入れ条件

### Business

向いている依頼:

- 何を優先すべきかを整理したい
- 誰の何を改善するのかを明確にしたい
- KPI、運用、組織、意思決定の前提を整えたい
- 機能よりも、業務価値や導入効果を整理したい

重くする論点:

- 利用者価値
- 期待効果
- KPI
- 運用変更
- 意思決定条件

### Hybrid

向いている依頼:

- 事業判断と実装判断が両方必要
- 誰のどの課題を解くかと、どう実装するかをつなぎたい

基本方針:

- デフォルトは Implementation
- 事業寄りの問いが主なら Business
- 両方が明確に必要なら Hybrid

## 3. High-Leverage Question Bank

以下から必要なものだけを選ぶ。

### Goal

- これがうまくいったとき、何がどう変わっていますか。
- その依頼で最終的に達成したい状態は何ですか。
- 成功したと言える条件を 1 から 3 個だけ挙げると何ですか。

### Problem

- 今いちばん困っていることは何ですか。
- それは誰にどんな不利益を与えていますか。
- 今はどうやってしのいでいますか。

### User and Stakeholder

- 主に使う人は誰ですか。
- 仕様の良し悪しを最終判断するのは誰ですか。
- 利用者は初心者寄りですか、熟練者寄りですか。

### Scope

- 今回やることと、今回はやらないことを分けるとどうなりますか。
- 最小スコープで価値が出る形はどこですか。
- 将来的に必要でも、今は外してよいものは何ですか。

### Constraints

- 絶対に守るべき制約は何ですか。
- 納期、予算、技術、運用の制約はありますか。
- 既存の仕組みに合わせる必要がありますか。

### Acceptance and Quality

- 完成判定は何で行いますか。
- どの失敗は許容できて、どの失敗は許容できませんか。
- 性能、精度、使いやすさで重視するものは何ですか。

### Examples and Non-Examples

- 具体例を 1 つ出すとどうなりますか。
- 逆に、それは違うと言える例は何ですか。
- 既存で近いものがあれば、何が良くて何が足りませんか。

## 4. Rescue Patterns

### User says "いい感じに"

抽象語を軸にしない。次のように分解する。

- 速くしたい
- 分かりやすくしたい
- ミスを減らしたい
- 手間を減らしたい
- 見た目を整えたい

どれが近いかを聞き、必要なら複数選ばせる。

### User says a solution only

例: 「チャットを付けたい」「AI を入れたい」「画面を一つ増やしたい」

返し方:

- その機能で何を解決したいですか。
- それがないことで今何が困っていますか。
- 他の方法でも同じ成果が出れば許容できますか。

### User cannot compare options

選択肢をこちらで構造化して返す。

- 速度重視
- 品質重視
- コスト重視
- 運用簡素化重視

どれを優先するかで要件が変わることを明示する。

## 5. When to Stop Asking

次を満たしたら、質問を増やすより要件定義ドラフトへ進む。

- 目的が一文で言える
- 成功条件がある
- 対象ユーザーが分かる
- 最低限の制約が分かる
- 今回の対象外が分かる
- 成果物モードを選べている

不足があっても、致命的でなければ仮説つきドラフトを出す。
ただし高曖昧度では、目的、成功条件、対象ユーザーの輪郭が出るまではヒアリングを優先する。
