# Deep Requirements Hearing

曖昧な依頼を、そのまま実装や回答に進めず、真の目的まで掘り下げて要件定義へ変換するためのスキルです。高曖昧度では、ドラフト化より先にヒアリングを優先します。

## When to Use

- ユーザーの指示が曖昧で、何を作るべきか、何を直すべきかが定まらない
- ユーザーが解決策だけを指定しているが、本当に解きたい課題が見えていない
- 依頼内容よりも、背景や成功条件のほうが重要そうに見える
- 要件定義、要件整理、ヒアリング、要求整理、clarification が必要
- 実装前に、目的、制約、優先順位、非目標を明確にすべき

## Core Principles

1. 依頼文面と本当の目的は分けて扱う。ユーザーが言った解決策を、そのまま問題定義とみなさない。
2. いきなり細部を聞かない。最初に「何を変えたいか」「なぜそれが必要か」を押さえる。
3. 質問は多ければよいわけではない。曖昧さを最も減らす質問から順に聞く。
4. 曖昧さが高い場合は、まずヒアリングを行う。必要情報が不足したまま仮説だけで仕様化へ進まない。
5. 最終成果物の重心は質問の性質で決める。実装目的なら実装寄り、事業目的なら事業寄り、両方ならハイブリッドにする。
6. 実装案より先に、成功条件と失敗条件を定義する。
7. 分からない点は推測してよいが、事実として断定せず、仮説として明示する。
8. ユーザーが言語化できていない場合は、選択肢や仮説を提示して思考を助ける。
9. 最終成果は「質問の羅列」ではなく、「進められる要件定義ドラフト」にする。

## Workflow

### 1. 依頼を二層に分ける

まず次の2つを切り分ける。

- 表面的な依頼: ユーザーが直接求めているもの
- 背後の目的候補: その依頼で本当に解決したいかもしれないこと

最初の応答では、必要に応じて次のように整理する。

- 依頼として見えている内容
- 本当の目的としてあり得る仮説を 1 から 3 個
- それを確定するための最少質問

### 2. 曖昧さのレベルを判定する

曖昧さは次の3段階で扱う。

- 低: 目的は明確で、入力、出力、制約の一部だけが抜けている
- 中: 目的は何となくあるが、対象ユーザー、優先順位、成功条件が曖昧
- 高: 解決策しか語られておらず、問題や期待成果がほぼ不明

レベルごとの進め方:

- 低: 不足項目だけを短く確認し、早めに要件定義へ進む
- 中: 目的、対象、成功条件、制約を中心に聞く
- 高: いったん実装や手段の話を止め、まずヒアリングに戻す。問題、期待成果、利用文脈の輪郭が出るまで仕様化しない

高曖昧度のルール:

- 最初のターンは質問と仮説整理を優先する
- 要件定義ドラフトは、目的、成功条件、対象ユーザーの輪郭が出るまで確定形にしない

詳しい質問設計は [references/question-playbook.md](./references/question-playbook.md) を使う。

### 3. 成果物モードを決める

ヒアリングを始める前か、早い段階で、成果物の重心を次の3つから選ぶ。

- Implementation: API、UI、データ、挙動、連携、例外処理、受け入れ条件を重くする
- Business: 利用者価値、業務変更、KPI、意思決定、運用制約を重くする
- Hybrid: 両方が重要で、事業判断と実装判断をつなぐ必要がある

選び方:

- デフォルトは Implementation
- ユーザーの問いが、業務、戦略、組織、KPI、価値検証寄りなら Business
- ユーザーの問いが、仕様、画面、API、データ、自動化、修正寄りなら Implementation
- 両方が混ざるなら Hybrid

以後の質問と要件定義ドラフトは、このモードに合わせて比重を調整する。

### 4. 高レバレッジ質問を優先する

質問は必要最小限に絞り、次の順で優先する。

1. 何がどう変われば成功か
2. 誰のどんな困りごとを解決したいか
3. 今は何が問題で、どんな代替運用をしているか
4. 絶対条件と、妥協できる条件は何か
5. 期限、優先順位、既存制約は何か

質問カテゴリ:

- Outcome: 期待する変化、達成したい状態
- Problem: 現状の痛み、なぜ困っているか
- Users: 利用者、関係者、意思決定者
- Scope: 対象範囲、非対象範囲
- Constraints: 技術、運用、法務、予算、納期
- Quality: 成功条件、品質基準、受け入れ条件
- Examples: 具体例、反例、避けたい振る舞い

### 5. 解決策先行の依頼を補正する

ユーザーが「この機能を付けたい」「この方法でやりたい」と言っている場合でも、以下を確認する。

- それは絶対制約か、単なる思いつきの手段か
- その手段で解きたい根本課題は何か
- もっと小さく、安く、早く解ける選択肢はないか

もし手段に引っ張られすぎている場合は、次の形で戻す。

- 今の要望を実現したい理由
- 実現後に変わっていてほしい業務や体験
- その変化を測る指標

### 6. ユーザーが言語化できない場合は仮説を出す

ユーザーが「うまく言えない」「いい感じにしたい」と表現した場合は、抽象語のまま進めない。

代わりに:

- 仮説を 2 から 4 個に分けて提示する
- それぞれの違いを短く示す
- どれが近いか、または何が違うかを返してもらう

例:

- 速度改善が目的なのか
- 誤操作削減が目的なのか
- 学習コスト低減が目的なのか
- 管理工数削減が目的なのか

### 7. 要件定義ドラフトに変換する

十分な情報が集まったら、質問を続けるのではなく、要件定義ドラフトにまとめる。

必ず含める項目:

- 要件定義モード
- 依頼の要約
- 推定される真の目的
- 対象ユーザーと利用シナリオ
- スコープ
- 非目標
- 主要要件
- 非機能要件
- 制約
- 受け入れ条件
- 未確定事項
- 次に確認すべき論点

出力時は [assets/requirements-definition-template.md](./assets/requirements-definition-template.md) の形を使い、Implementation、Business、Hybrid のどれかに応じて必要な欄を厚くする。基本は Implementation を優先する。

### 8. 前に進めるかを判定する

最後に、次のどちらかを明示する。

- この情報で実装や設計に進める
- まだ止めるべき。理由はこの未確定事項が致命的だから

未確定事項は、重要度順に並べる。単なるメモ列挙で終わらせない。

## Output Format

回答は原則として次の順でまとめる。

1. 見えている依頼
2. 推定される真の目的
3. 確認したい質問
4. モード別の要件定義ドラフト
5. 未確定事項と次の一手

## Completion Criteria

このスキルは、次を満たしたとき完了とみなす。

- ユーザーが表面上求めたものと、解きたい本質課題が区別されている
- 高曖昧度なら、最初にヒアリングから入れている
- 成功状態が具体的に言える
- 対象ユーザー、制約、優先順位が整理されている
- 成果物が Implementation、Business、Hybrid のどれかで意図的に整形されている
- 非目標が定義されている
- 実装や設計に使える要件定義ドラフトがある
- 未確定事項が重要度つきで整理されている

## Guardrails

- 長すぎる質問票を最初から投げない
- 背景不明のまま、いきなり仕様を断定しない
- ユーザーの言い回しをそのまま要件名にしない
- 重要な前提を暗黙のまま進めない
- 「とりあえず全部盛り」の要件定義にしない
